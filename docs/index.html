Why it works this way

First steps (101)

Just installed TxUI? This is the short path from the start screen to your first query result. Five minutes, no manual — the details live in the main guide and the per-engine guides linked at the bottom.

TxUI is a desktop database GUI: one window for connections to MySQL / MariaDB / Percona, PostgreSQL, Redis, ClickHouse, SQLite, DuckDB, Parquet files, MongoDB and SQL Server. It runs entirely on your machine — there is no server component and nothing leaves it.

One notation note: Mod means ⌘ Command on macOS and Ctrl on Windows/Linux. Every shortcut in the app is defined that way, so Mod+Enter below is ⌘Enter or Ctrl+Enter depending on your OS.

1. The start screen

Launch TxUI. With no connections saved yet, the window is a sidebar on the left and a welcome prompt that lists the same five steps this guide walks through. The Output pane at the bottom logs every connect/test attempt — if something fails, the error lands there, copyable.

No database server to hand? Click 🦆 Scratch buffer in the sidebar (or on the welcome screen): an in-memory DuckDB session where you can run SQL immediately, or query a CSV/Parquet/JSON file directly (SELECT * FROM '/path/to/file.csv'). It is the fastest way to see a first result, and it needs no connection at all.

2. Create your first connection

The five steps the welcome screen shows:

  1. Right-click empty space in the sidebar → New connection… — or click the + button at the top of the sidebar, or press Mod+Shift+N.
  2. Choose the engine and fill in host, port, user and password. Empty fields use the engine default — defaults show as greyed placeholders, never prefilled text. Pasting a connection URL (postgres://…, mysql://…) fills the form in one step.
  3. Click Test to check the config without saving…
  4. …then Save. Your password goes into the per-machine secrets store, never into the readable config file.
  5. Double-click the connection in the sidebar to open it.

Two optional fields are worth knowing from day one: Environment (tag a connection prod and TxUI adds confirmation prompts and hard limits around writes) and Read-only (blocks all writes, enforced before anything reaches the server).

File engines are simpler: pick SQLite, DuckDB or Parquet and the form collapses to a file picker — no host, port, user or SSH.

3. The workspace

Connecting opens a session:

  • Left: the object explorer — databases → type groups (Tables, Views, …) → objects → columns and indexes. Click a name to insert it into the editor.
  • Middle: SQL editor tabs — one query tab opens on connect; Mod+T adds more. Completion proposes tables and columns as you type.
  • Bottom: the result area — grid, chart and log views for whatever you run.
  • 📓 Log tab — every session records everything it does: what ran, how many rows, how long it took, and every error. When something surprises you, look here first.

4. Run your first query

Type a statement in the editor — SELECT * FROM … — and press Mod+Enter to run the statement at the cursor (or the selected text). The result lands in the grid below: sortable, filterable, and fast even at a million rows.

Mod+Shift+Enter runs the whole buffer. Mod+E shows the execution plan of the statement at the cursor.

5. Browse a table

Double-click a table or view in the object explorer to open the data browser: a read-only paged grid of the table's rows (latest first), with per-column filters and foreign-key click-through — click an FK value to open the referenced row.

The browser is read-only by design — there is no cell editing, so exploring a production table through it cannot change anything.

6. Settings

Mod+, (or the ⚙ button) opens Settings: theme and font size, editor behaviour, connection timeouts, safety limits. The defaults are sane; come back when something nags.

ClickHouse

TxUI speaks to ClickHouse over the HTTP interface, not the native protocol. A ClickHouse session gives you the full SQL editor, the object explorer, the data browser, and a large set of system.*-based DBA views.

Connect

  1. Sidebar + (or File → New Connection, Mod+Shift+N).
  2. Set Engine to ClickHouse.
  3. Fill in:
    • Host / Port — default 8123 (plain HTTP). Use 8443 for HTTPS. The native protocol ports 9000/9440 do not work — TxUI does not speak the native protocol. If you paste a URL with one of those ports, the form warns you. This is usually the right default anyway: 9000 is frequently load-balancer-only or closed, while 8123 is what ingresses expose.
    • User / Pass — default user default.
    • Database — default default. The session's database picker switches database per request (there is no USE over HTTP).
    • SSL — Require/Verify CA/Verify Full use HTTPS and honour a custom CA (ssl_ca_path). With Preferred, the scheme is committed by port: 8443/9440 → HTTPS, anything else → plain HTTP.
    • SSH tunnel — supported.
  4. Or paste a URL: clickhouse://user@host:8123/db?readonly=1 and clickhouse+https://… fill the form — readonly=1 ticks the READ-ONLY box, secure=1 enables TLS, and any other query param is kept as a session setting.
  5. Test, then Save.

Double-click the connection to open a session.

The session

A ClickHouse session: object explorer on the left, SQL editor and results on the right, DBA tools in the toolbar.

Everything in the main guide applies: the SQL editor with ClickHouse dialect and backtick identifier quoting, Mod+Enter to run, the default LIMIT guard, the data browser (double-click a table in the explorer), the 📓 Log and 📜 Audit log. While a query runs, the toolbar shows live read progress (rows and bytes read) next to the ■ Cancel button; Cancel drops the HTTP request and the server cancels the query (cancel_http_readonly_queries_on_client_close).

Processes

The ⚡ Processes panel (toolbar or Tools menu) reads system.processes live — what is running, for how long, from which user — with a filter box and kill (KILL QUERY, audited to the 📓 Log and 📜 Audit log like every kill).

DBA views — 47 of them, system.* only

Open 🩺 DBA Views from the toolbar or the Tools menu. Every view reads only system.* tables, so all of them work on a read-only connection. Highlights:

  • Parts & storage — parts and levels per partition, detached parts, per-column compression (compressed vs raw bytes and the codec), a per-table overview, partitions, key columns, LowCardinality candidates.
  • In-flight work — running merges and mutations, the slowest / heaviest / failing queries from system.query_log, recent part events.
  • TTL — TTL policies and TTL debt (overdue parts the merge has not reclaimed).
  • Cluster — topology, replication and distributed queues, the Keeper session, replicas.
  • Server health — the server's own warning list, error counters, the server log at warning-and-above, metrics, asynchronous metrics, events, settings, disks, grants, row policies and quotas.

Columns are click-sortable, the row limit is choosable (100 / 1k / 10k / ∞), and Cancel kills a slow view query server-side.

Server Tuner

The 💊 Server Tuner has a ClickHouse rule set over the same system.* operational tables, with the same health score, findings and Markdown report export as the MySQL/PostgreSQL tuners — fully read-only, fixes are generated for you to copy, never executed.

Read-only, taken seriously

Tick READ-ONLY on the connection and every request carries readonly=1: the server refuses writes (Code: 164 … Cannot execute query in readonly mode), and the setting cannot be lifted from inside a session — SET readonly=0 and SELECT … SETTINGS readonly=0 are both rejected. The price: readonly=1 also freezes session settings, so a SETTINGS clause on a plain SELECT is refused too — the error message says so explicitly.

What a ClickHouse session does not have

  • No transactions — the ⚡ AUTO / ● TX controls are absent; ClickHouse has no interactive transactions.
  • No ER diagram, data generator, CSV import, or SQL Quality panel — these are built on MySQL/PostgreSQL catalogs, so they are not offered.
  • No dump/restore panel — the external dump tools TxUI drives are MySQL/PostgreSQL binaries.

MySQL / MariaDB / Percona

Everything in TxUI that is specific to the MySQL family. Shared features (result grid, saved queries, history, themes) are covered in the main guide.

Connecting

  1. Sidebar → + New Connection (or File → New Connection, Mod+Shift+N).
  2. Set Engine to MySQL (same driver covers MariaDB and Percona Server).
  3. Fill Host / Port / User / Password. Empty fields use the engine default (port 3306); defaults show as greyed placeholders, never prefilled text.
  4. Optionally set a default Database — unqualified table names resolve there.
  5. SSL: pick the SSL mode and supply CA / client cert / client key if your server requires them.
  6. SSH tunnel: enable and give host/port/user/key, or password/passphrase auth; an optional jump host is supported. Every session (and every dump run) then dials through the tunnel.
  7. Open Advanced for connect/pool timeouts, the client-side query deadline, per-engine extra_params, and a unix socket path for local servers.
  8. Paste a mysql://user:pass@host:3306/db?… URL into the form to fill it in one step; unknown query params land in Advanced with a warning.
  9. Click Test to verify, then Save. Double-click the connection to open a session.

The password lives in the encrypted vault (vault.txui), never in the config file, never in process arguments.

Set Environment (dev/test/prod) and the read-only flag here — they drive the safety model described below. Give the connection a folder (folders group the sidebar; a folder can be marked as a replica set) and labels (prod-eu, cz-test — the handle every fleet function runs on).

Object explorer

The tree under a session shows databases → type groups → objects → columns/indexes. Groups appear only when non-empty, with counts. For MySQL you get Tables, Views, Functions, Procedures, Triggers, and Events (MySQL-only).

  • Click a name to insert it into the editor.
  • Double-click a table/view → opens the read-only Data browser (latest rows first, LIMIT 100). Double-click a routine/trigger/event → its DDL.
  • Right-click → DDL, refresh; right-click a table also offers virtual foreign keys (declared locally, never written to the server — they power JOIN completion and the ER diagram on FK-less schemas).
  • ↻ refreshes the tree and the completion metadata cache.
  • Indexes show their key list including expression keys.

SQL editor specifics

  • MySQL-dialect syntax highlighting, completion, lint and hover. USE completes databases; SHOW offers the full SHOW-statement catalog; CALL completes procedures.
  • @@variables complete with their current values; MySQL optimizer hints (/*+ … */) are offered in context.
  • FK-powered JOIN clauses after JOIN (both directions), with name-convention fallback clearly labelled as a guess.
  • A MySQL DELIMITER directive inside a script is honoured from that line on (needed for procedure bodies), on top of the global statement-delimiter setting.
  • Mod+Shift+8 expands *; F12 opens the table under the cursor; Mod+E explains the statement at the caret.
  • Cancel kills the running statement server-side (KILL QUERY), it does not just drop the client request.
  • Manual transactions: click ⚡ AUTO to open a transaction on a pinned connection; Commit/Rollback sit next to Run. With autocommit off set on the connection, the session pins one connection and keeps a transaction open for its whole life — the toolbar shows the server's own @@autocommit and flags ⚠ when it disagrees with the setting.

DBA panels

Every panel opens as an ordinary tab: toolbar button (hover for tooltips), Tools menu, or Mod+K by name. Several can be open at once; a busy tab shows ⟳; closing a tab that is still running something asks first.

⚡ Processes — processlist & kill

Live SHOW FULL PROCESSLIST with auto-refresh (1–30 s), filter box, Kill query / Kill connection buttons. A long ≥ N s threshold (default 30) tints rows yellow, ≥2× red; tick only long to filter, or ⏱ longest to sort longest-first.

Faster path: type kill in the SQL editor — a live processlist popup opens at the caret (1 s poll, running work longest-first). ↑↓ move, ⇥ mark several, ⏎ kills, ⇧⏎ inserts KILL <id> into the editor instead, Esc closes. kill … kills the connection; kill query … kills only the statement — the footer says which. A glyph column marks ⛓ blocking / ⏳ waiting / ● open transaction (details on hover), and ↑n shows how much each thread aged while you watched.

Type killall for lock-chain analysis instead of a blind massacre. It identifies — with the evidence listed — the root blocker of a lock queue (never its victims: MySQL reports every waiter as blocking the ones behind it), a rogue family (2+ threads, same user, same statement digest, all ageing), or an idle transaction holding locks. Nothing is pre-marked when nothing qualifies.

Every kill, from any surface, writes one audited line naming everything known about the victim to the session 📓 Log and the 📜 Audit log. Own and system threads are visible but never killable; on prod the first ⏎ only arms.

🔒 Locks

Live blocking chains from sys.innodb_lock_waits: who waits on whom, wait age, both statements, one-click Kill blocker. Plus the deadlock analyzer: the server's latest InnoDB deadlock parsed per transaction (raw section available). 5 s auto-refresh with pause.

⇄ Replication

Multi-channel aware: one summary row per channel — IO/SQL thread state, seconds-behind, source — with stopped channels tinted. Expand a row for positions, GTIDs, filters and error rows; "all fields" dumps everything. A prominent collapsed-channel alert appears the moment a thread isn't running, quoting the actual Last_SQL/IO_Error text (which names the failing table/query). Auto-refresh 5 s with pause; each poll stamps updated HH:MM:SS.

🔁 Replica set dashboard

Right-click a connection folder → treat as replica set; star the primary. Open the dashboard: it connects to every member read-only and shows the replication matrix (role / lag / IO / SQL / errors, worst first, 5 s poll), the unused-index intersection (indexes unused on every member are the safe drop candidates — per-member uptimes shown as the caveat), and config & version drift side-by-side with differences highlighted. Sessions close when the dashboard closes.

ⓘ Server variables & status

Searchable variables and status counters. Compare against defaults, find the knob, copy the name.

📈 Monitor

Re-run any query on an interval and watch metric cards (value, Δ/s rate, sparkline; click a card for a full-size history chart). Ships with DBA presets for the usual counters.

🩺 DBA views — sys / performance_schema

~30 curated read-only lookups over sys and performance_schema: top statements (numeric ms latency, full digest text), unused indexes, lock waits, full-table-scan list, per-host/per-user statement summaries, realtime events_statements_current, and more. Choose the row limit (100/1k/10k/∞), click column headers to sort, Cancel kills the query server-side. The Lock instrumentation status view confirms lock data is actually collected before you trust an empty lock view. Demanding views carry a ⚠ badge with the reason.

⏱ Watch

One panel, three modes (Activity → Watch). Metrics: re-run any query on an interval; metric cards with value, Δ/s rate, sparkline. Statement: run one statement in a narrow editor with a big live elapsed timer; the right pane polls the processlist and shows your thread's phase (State / performance_schema stage) with a progress % where the server estimates one — long ALTERs are watchable phase by phase. Cancel = KILL QUERY. A detected-long-queries list (threshold, default 60 s) tracks queries as they cross it, each with Kill (audited), Explain (plain EXPLAIN, never ANALYZE) and Copy. 👁 Watch on a Processes row pins this mode to a thread started elsewhere — same phase/progress poll, read-only.

Execution plans — EXPLAIN visualization

Select a statement → Explain button or Mod+E. Four views of the same plan:

  • Graph — bottom-up diagram, cost-tinted boxes, row-volume-weighted edges; pan/zoom/fit, collapsible subtrees, per-node inspector explaining what the operation does.
  • Cost — icicle view, width = cumulative cost.
  • Tree — indented tree-table with metric columns.
  • Raw — untouched server output.

A banner states whether timings are measured (EXPLAIN ANALYZE) or estimated. Plan findings call out full scans over large tables, missing indexes, filesort/temp tables, nested loops over large outer inputs — each with what was observed and what to do. Plan stability scores (0–100) whether the plan will hold; Plan → Compare diffs two recorded runs of the same statement shape ("did my index help?").

⏱ Profile (MySQL-only, in the plan tabs): SHOW PROFILE for the statement just run — where time went inside one query. Misleading MySQL state names are translated (Sending data means reading rows, not network).

🩹 Maintenance

Platform notes — macOS, Linux, Windows

TxUI ships the same features on all three desktop OSes, with two registered exceptions (below). The differences below are install, shortcuts, feature availability and file locations.

Shortcuts: one modifier difference

Every shortcut in the app and in this guide is written as Mod:

  • macOS — Mod is ⌘ Cmd.
  • Linux / Windows — Mod is Ctrl.

So Mod+Enter is ⌘↵ on a Mac and Ctrl+Enter elsewhere. The in-app Help → Keyboard Shortcuts (Mod+/) list and every tooltip are labelled with the right key for the OS you are on, automatically.

Feature availability: the two registered gaps

Everything works everywhere except two genuinely platform-bound features (the table the app itself consults lives in src/utils/platformCaps.ts). An unavailable feature is never hidden — the control is greyed, and the hover tooltip names the reason and the workaround:

FeaturemacOS / LinuxWindows
Unix socket connections✓✗ — the OS has no Unix domain sockets; MySQL uses a named pipe there and PostgreSQL is TCP-only. Connect over host/port instead.
mydumper / myloader (MySQL dump tools)✓✗ — upstream ships no Windows build. Use mysqldump / mysql instead; the dump panel offers them.

Smaller per-OS differences, all handled for you:

  • Dump-tool discovery probes per-OS locations: Homebrew/MacPorts paths and the executable bit on macOS/Linux, .exe/.bat names on Windows. The "not installed" hint names the right package manager for your OS (brew, apt/dnf, or the MySQL/PostgreSQL installers).
  • SSH tunnels work on all three. On Windows the password helper is a .cmd file driven by SSH_ASKPASS_REQUIRE=force (a shebang script would not run there); on macOS/Linux it is a /bin/sh script. Either way the password travels in the child's environment, never in arguments.
  • TxShell ! passthrough runs through your own shell: $SHELL (fallback /bin/sh) on macOS/Linux, %ComSpec% (fallback cmd.exe) on Windows — so !dir on Windows and !ls elsewhere both mean what they mean in your terminal.
  • Export line endings default to CRLF on Windows, LF elsewhere — a default, not forced; the export CRLF setting overrides it.

  3. Click a key to inspect it.

Inspect and edit a key

The detail pane shows a colour-coded type badge (STRING / LIST / HASH / SET / ZSET / STREAM), the key name, and its size — bytes for strings, item count for collections.

  • String — edit the value in the textarea, click Save (SET).
  • List — items with their index.
  • Hash — a field/value table.
  • Set — members as chips.
  • Zset — a score/member table.
  • Stream — one row per entry, one column per field (the union of all fields across the loaded entries).

Only string values are editable in place; collection types are viewers.

TTL

The TTL row shows the remaining lifetime, humanized (2d 4h, 15m 3s), ∞ persistent for no expiry, (expired) for a key that is already gone. Click Edit, enter seconds — or -1 (or empty) to remove the expiry (PERSIST) — and press Enter or Set.

Delete

Click 🗑 Delete in the key header and confirm. The key leaves the list immediately.

Server INFO

Switch to the Server INFO tab for the server's INFO parsed into its sections (Server, Clients, Memory, Persistence, Replication, …) as name/value tables. Click ↺ Refresh to re-read.

Server panels

The Tools menu opens the Redis-capable DBA panels as extra tabs in the browser; picking the same item again (or the tab's ×) closes it:

  • ⚡ Processes — the connected clients from CLIENT LIST, with auto-refresh and Kill connection (CLIENT KILL; TxUI's own connection is refused).
  • ⓘ Server variables & status — CONFIG GET and INFO, searchable.
  • 🩺 DBA views — a curated set of Redis commands: slowlog, memory (MEMORY STATS, MEMORY DOCTOR), latency, keyspace, modules, ….
  • 💊 Server tuner — a dedicated Redis rule set over INFO/CONFIG, with fixes worded for redis.conf.

Anything the menu offers that Redis cannot do (SQL-editor panels, the playground, …) is ignored on a Redis session rather than opened broken.

Safety on Redis

Writes from the browser (Save, Set TTL, Delete) are checked server-side:

  • Read-only connections refuse them all — and the command-level guard covers the destructive surface (FLUSHALL, FLUSHDB, CONFIG SET, …), not just the obvious writes.
  • Prod connections additionally block FLUSHALL/FLUSHDB, SHUTDOWN, REPLICAOF, FAILOVER and DEBUG, and refuse KEYS with a pointer to SCAN.

What a Redis session does not have

No SQL editor, no object explorer, no ER diagram, no data generator, no CSV import — none of these exist for a key/value store, so the controls are not offered.

SQLite, DuckDB & Parquet files

All three are opened by path, not dialled: pick SQLite (file), DuckDB (file or :memory:) or Parquet (file) as the engine and the connection form collapses to a file picker — host, port, user, password, SSL and SSH all disappear, because none of them mean anything for a file.

Open a file

  1. Sidebar + (or File → New Connection, Mod+Shift+N).
  2. Set Engine to SQLite (file), DuckDB (file or :memory:) or Parquet (file).
  3. Click Browse… and pick the file (the picker is filtered to the engine's extensions: .sqlite/.sqlite3/.db/.db3, .duckdb/.ddb/.db, or .parquet/.parq/.pq), or type the path.
  4. Save, then double-click the connection.

A missing SQLite or DuckDB file is an error, never a silently created empty database — a typo in a path must not produce one.

Create a new SQLite database

In the connection form, click New… beside the file picker and choose a path. The file is created with the settings it should have started with — WAL, synchronous = NORMAL, foreign keys on — rather than SQLite's defaults. Creating over an existing file is refused.

There is no "new empty Parquet": the format is immutable, so creating one means writing it completely — Export → Parquet on any result grid, from any engine (ZSTD compression, 128k-row row groups, statistics on; column types inferred across every value, so one string in an integer column makes a string column, not a truncated one).

For DuckDB the equivalent is :memory: plus SQL: click the :memory: button in the form (or type it as the path), connect, then ATTACH 'path.duckdb' and create tables in the attached database.

SQLite — a full engine

A SQLite session: the object explorer shows attached databases, tables, views and triggers; the editor runs full SQL.

Everything in the main guide applies:

  • Object explorer — attached databases → tables, views, triggers → columns and indexes. Double-click a table for the read-only data browser; right-click for DDL (the stored text, verbatim).
  • SQL editor — full SQL with schema-aware completion, including foreign-key-driven JOIN suggestions. Writes work on a normal connection: INSERT/UPDATE/DELETE/DDL run and report affected counts.
  • 🔬 Explain — EXPLAIN QUERY PLAN for the statement at the caret.
  • 🩺 DBA Views — 15 views: real on-disk bytes per object from dbstat, index-vs-table space, foreign keys with no index on the child side, tables with no PRIMARY KEY, integrity and foreign-key checks, planner statistics, and the durability pragmas.
  • Manual transactions — the ⚡ AUTO / ● TX toggle, Commit and Rollback work as on any SQL engine.
  • 🕸 ER diagram — SQLite's declared foreign keys (plus any virtual FKs you add locally) lay out like any other schema.

Read-only is enforced by SQLite itself, not by a client-side guard: a READ-ONLY connection opens the file with mode=ro, so INSERT, CREATE TABLE and friends fail with SQLite's own read-only error while SELECT keeps working.

DuckDB — an in-process OLAP engine

A DuckDB connection is a full SQL engine over a file — or over :memory:, which is the normal way to query Parquet/CSV/JSON:

SELECT * FROM read_parquet('s3://bucket/data/*.parquet') LIMIT 100;
  • Object explorer — attached databases → tables, views and macros, named schema-qualified (main.orders) because DuckDB is three-level (db.schema.table) and ATTACHed databases routinely share a main schema. Columns, indexes, PK/FK metadata and the stored DDL all show; double-click opens the read-only data browser.
  • SQL editor — the Postgres-flavoured dialect (double-quoted identifiers; DuckDB rejects backticks), with completion for the catalog and DuckDB's own vocabulary (PIVOT, QUALIFY, the file readers, …). Writes work on a normal connection.
  • 🔬 Explain — EXPLAIN / EXPLAIN ANALYZE render as text plans.
  • ⓘ Server variables — duckdb_settings() with its GLOBAL/LOCAL scope.
  • 🩺 DBA Views — 10 views: attached databases, version & context, settings, extensions (loaded vs installed), tables by exact row count, views, all columns, indexes with their CREATE statements, enforced constraints, user macros, and sequences.
  • Manual transactions — BEGIN / COMMIT / ROLLBACK work as on any SQL engine. Cancel is real: DuckDB's interrupt handle is its in-process equivalent of KILL QUERY.

Read-only is enforced by DuckDB itself, not by a client-side guard: a READ-ONLY connection opens with access_mode = READ_ONLY, so the engine refuses the write. One read-write process per file is DuckDB's own locking; a second read-write session to the same path fails at open with DuckDB's lock error (read-only sessions share freely).

Not available (greyed or refused by name, never silently broken): the processlist and kill (in-process — there is no other connection), replication, the playground, dump/restore, the tuner, the CSV import wizard (DuckDB imports in SQL: COPY … FROM / read_csv()), the table designer and view editor (no DuckDB dialect in either yet), and the default-database picker.

Parquet — a deep read-only inspector

A Parquet file: leaf columns with physical/logical types, row groups, per-chunk encodings and statistics.

Parquet is a file format, not a database — TxUI treats it as an inspector, deliberately:

  • Browse rows — double-click the file in the explorer to page through rows. Row groups that end before the requested offset are skipped, so paging deep into a large file stays fast. No filters or sort — there is nothing to run them.
  • File metadata — format version and writer, leaf columns with physical/logical type and repetition, per-row-group size and compression ratio, per-column-chunk codec, encodings, min/max, null and distinct counts, bloom-filter presence. Reading this is O(footer), not O(file).
  • 🩺 15 metadata views, including a File health report (row-group sizing, columns with no statistics, dictionary fallback, missing page index or sort order), per-page statistics from the page index, encodings, bloom filters, codecs, size skew, null density and cardinality.
  • SQL is refused by name — SELECT … against a Parquet connection fails with "Parquet is a file, not a query engine", rather than being half-parsed into something that silently returns wrong rows. What the editor does accept is the Parquet command vocabulary — FILEINFO, SCHEMA, ROWGROUPS, COLUMNCHUNKS, STATS, PAGES, ENCODINGS, CODECS, NULLS, CARDINALITY, SKEW, SORTING, BLOOM, HEALTH, KEYVALUE, PREVIEW n — the same inspections the DBA-views panel renders. Nested columns (structs, lists) are shown flattened to leaves (addr.city), which is what the format stores.

What file sessions do not have

There is no server, so there are no server-side panels: no processlist, no monitor, no tuner (SQLite's are file-local pragmas, covered by the DBA views above; DuckDB's settings show in ⓘ Server variables via duckdb_settings()). The data generator is not offered on file sessions — its writers speak the MySQL/PostgreSQL wire protocols only. CSV import works on SQLite (batched INSERTs in one transaction, like the other engines); a Parquet file is immutable, so nothing imports into it; and DuckDB imports in SQL (COPY … FROM / read_csv()), so the wizard is not offered there either. SQL Quality on SQLite and DuckDB runs its static lint; the server-side EXPLAIN checks are MySQL/PostgreSQL-only. The data browser is read-only, as it is everywhere.

The workspace

Open a connection (double-click it in the sidebar) and you land in a session workspace: the object browser, a multi-tab SQL editor, and the result grid. Each session records everything it does in its own Log tab.

Running SQL

  • Run the statement under the cursor with ⌘↵Ctrl+Enter. Select text first to run only the selection.
  • Autocomplete proposes tables, columns, keywords and snippets as you type.
  • Transactions: switch off AUTO to work in an explicit transaction, then Commit or Rollback. The current autocommit state is always shown.
  • Result grid: sort, filter per column, copy, export, chart or pivot — and switch to the record view for a single row.

Vacuum & Bloat

PostgreSQL

PostgreSQL maintenance, in the order the question is actually asked: is anything vacuuming NOW, what is the BACKLOG against each table's own threshold, how much space is wasted (BLOAT), how close is the WRAPAROUND emergency, and what to DO about it. The backlog is ranked against each table's OWN reloptions-honoured autovacuum threshold rather than a global rule of thumb, so a table with custom settings is judged by its own settings. Bloat figures are estimates by default and exact when pgstattuple is installed, and the panel says which it is showing. Availability & known limits

TxUI is honest about what a given engine, platform or environment allows. When a feature can't run, the app tells you why rather than failing silently.

  • Engine gating. Panels and commands appear only for engines that support them (see the engine matrix). A menu item greyed out with a tooltip means the current engine (or your role) doesn't allow it.
  • Redis / Parquet. No SQL editor for Redis; Parquet is a read-only in-memory scan — writes, transactions and DBA tooling are not available.
  • Live-connection panels. Monitoring panels (Processes, Locks, Wait events, Listen/Notify, Statement statistics, Replication, Binary logs…) need an active server and real activity; in this offline documentation build their screenshots are marked NA.
  • Cloud SQL (IAM). Service-account IAM auth is supported but requires a valid GCP key at runtime — not tested in this build.
  • Cross-platform shortcuts. Every shortcut is defined once with Mod and rendered per-OS — there is no macOS-only or Windows-only chord.
